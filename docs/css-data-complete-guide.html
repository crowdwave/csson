CSSON v1 · the complete guide

CSSON — data that is also CSS

CSSON is structured data written as a valid CSS stylesheet. Because a .csson file is CSS, a browser already knows how to parse it — you read your data straight out of the browser's built-in CSSOM, with no library and no extra parser.

01The idea

A CSSON document is one tree of nodes. Each node is a CSS style rule; its fields are custom properties (--key); its children are nested style rules. Repeated sibling rules of the same type form an array. That is the whole format — nothing is invented on top of CSS.

CSSON deliberately exposes only what a real CSS parser already gives you. Implementations never write their own CSS parsing — the browser (or lexbor, in the native core) does it, and CSSON just walks the result.

02The data model

  • Object — a style rule: type { … }. The selector is the key under its parent.
  • Field — a custom property: --key: value; → "key": value.
  • Object array — repeated sibling rules of the same type, in source order.
  • Scalars — string (double-quoted "Bob"), integer (3, -7), and identifier (an unquoted token read as a string, e.g. active).

There are no value-arrays: a field holds a single scalar. A list of things is expressed the native CSS way — as repeated child nodes.

  object arrays in source order. Two engines reading the same document produce
  byte-identical output.


  
05Reading it — the authored rule tree

  
CSSON is read from the authored rule tree — the stylesheet's
  cssRules, exactly as written. The reader is tiny and dependency-free:

  
// the whole reader — browser built-ins only
function cssonCanon(sheet){
  const sel = r => r.selectorText.replace(/^[&\s]+/,'').trim();
  const coerce = s => { s=s.trim();
    if(/^-?[0-9]+$/.test(s)) return parseInt(s,10);            // integer
    if(s[0]=='"'&&s.at(-1)=='"') return s.slice(1,-1); // string
    return s;                                            // identifier / verbatim
  };
  const node = r => { const o={}, st=r.style;
    for(const p of st) if(p.startsWith('--')) o[p.slice(2)]=coerce(st.getPropertyValue(p));
    for(const c of r.cssRules||[]) if(c.selectorText!==undefined)(o[sel(c)]??=[]).push(node(c));
    return o;
  };
  let out; for(const r of sheet.cssRules) if(sel(r)==='csson') out=node(r);
  const canon = v => Array.isArray(v)?v.map(canon)
    :v&&typeof v=='object'?Object.keys(v).sort().reduce((a,k)=>(a[k]=canon(v[k]),a),{}):v;
  return JSON.stringify(canon(out));
}

  
Never getComputedStyle. Reading through the
  cascade collapses duplicate keys to a last-wins value and discards source order — which would
  destroy arrays. Conforming readers walk the authored cssRules tree only.


  
06Scalars & fidelity

  
A field value is the verbatim source token, then coerced: all digits (with an
  optional -) become an integer; a double-quoted token becomes a string; anything else
  stays a string. Because the value is taken verbatim, floats, exponents and units survive
  losslessly — 1.618 and 1e3 read identically in every engine, never
  rounded or reformatted.

  
An optional @property --key { syntax: … } rule declares a field's type as inline,
  travelling-with-the-document schema. It is advisory: it does not change how the
  structure is read, only how a tool may validate or strongly type scalars.


  
07Loading a .csson file

  
A CSSON file uses the .csson extension and is served as
  Content-Type: text/css so the browser parses it as a stylesheet.

  
<!-- already in the page -->
<link rel="stylesheet" href="data.csson">
<script type="module">
  import { toCanonicalJson } from "csson";
  const json = toCanonicalJson(document.styleSheets[0]);
</script>

// or from fetched text, without touching the page:
import { fromText } from "csson";
const json = fromText(await (await fetch("data.csson")).text());


  
08Editing without losing comments

  
CSSON edits operate on the source text, never by re-serializing the CSSOM —
  serializing a stylesheet (e.g. cssText) strips comments and reformats. The native
  csson core edits in place by splicing the source bytes at parser-provided offsets, so
  comments and formatting survive; it supports set, rm, and RFC 6902
  JSON Patch. In the browser, the same comment-preserving edits come from the core compiled to
  WebAssembly.

CSSON earns its place where CSS is already the transport (design-token systems, themeable apps,
  anything with a stylesheet parser on hand). For greenfield data, JSON/TOML/YAML have deeper tooling.
